## Priority findings

1. **P1 — persisted HTML can execute in the app origin.** `src/App.tsx:127` renders note/exam bodies through `dangerouslySetInnerHTML`; note saving at `:263`, exam saving at `:272`, and schedule-note saving at `:212` retain arbitrary strings. No sanitizer exists in the source. The isolated probe confirms an image's `onerror` attribute reaches the HTML sink unchanged. A user pasting untrusted HTML into these textareas can persist executable markup, with access to every profile in the same origin's storage. Render plain text where formatting is unnecessary; otherwise allowlist formatting and URLs before storage/render. Test event attributes, SVG handlers, script URLs, malformed HTML, and normal bold/italic content with a harmless marker in an isolated test browser.

2. **P1 — editing across a profile switch moves records into the wrong profile.** The children at `src/App.tsx:165`, `:167`, and `:168` are not keyed by profile. Editor state at `:217`, `:257`, and `:269` retains the old record ID when only props change. Save at `:224`, `:263`, and `:272` overwrites that ID with `profileId: profile.id`, using the new profile. Actual NotesPage and ExamPage component probes reproduce A→Edit→B→Save transferring A's original record to B and retaining A's subject ID. Reset or remount profile-bound editors; validate both record ID and owner at each write. Test every editor, unsaved new drafts, delete/undo, and empty-profile subject choices across switches. Related: schedule notes at `:212` select `d.subjects[0]` globally instead of the active profile's subject.

3. **P1 — corrupt-save recovery overwrites the only recoverable copy, and failed writes are unhandled.** `src/App.tsx:80` catches JSON/migration failures and silently returns seed data; the unconditional mount/change effect at `:145` writes that seed to the same key. A corrupt current save also prevents trying a valid legacy save because one try/catch surrounds both reads. The isolated probe reproduces replacement of the corrupt raw bytes. `normalizeData` at `:58` validates neither the full schema nor a nonempty profiles array; an empty profiles array reaches `:150–151` and causes an undefined-profile error. The save effect itself catches neither quota nor blocked-storage failures, has no save status, and no recovery copy. Preserve failing raw data, validate before committing, recover from a separate last-good snapshot, and expose failed saves. Test corrupt JSON, malformed/empty profiles, valid legacy fallback, quota exceeded, blocked storage, and persistence after a failed write.

4. **P1 — two open tabs can overwrite each other's work.** `src/App.tsx:144` initializes an independent in-memory AppData snapshot; `:145` replaces the entire shared localStorage record after any change. No `storage`/BroadcastChannel listener, revision check, merge, or single-tab lock exists in the source. Tab A adds a note; stale tab B changes a checkbox or theme; B writes its stale whole snapshot and deletes A's note from persisted data. Test two app instances making disjoint and conflicting edits; use revision-aware storage or an explicit supported single-writer mode.

5. **P2 — Restore Summer resets checkboxes but can resurrect old progression immediately.** `src/App.tsx:330` replaces Summer tasks with `done:false` seed tasks while retaining that profile's stored sanctuaryProgress. The derived display at `:152` shows Stage 0, but `toggleTask` at `:160` reads the stale stored state. An isolated probe confirms 45 credits → Restore → displayed 0 → complete one task → 45 credits again. Commit a matching new progress state within the restore update. Test restore→complete one before reload, after reload, all other profiles preserved, and recovery/undo for custom Summer tasks that restore removes.

6. **P2 — bulk completion invents completion dates from due dates.** `src/App.tsx:161` sends each task's due date at 18:00 as `completedAt`, whereas individual toggles at `:160` use the actual completion time. `src/game/progression/progressionEngine.ts:217` records those dates, and `:73` counts distinct dates for lantern progression. One bulk click across 14 due dates therefore grants 14 active days; clicking the same tasks individually today grants one day. Test bulk versus individual completion equivalence and agree on whether the feature means actual study days or scheduled days.

## Local-only boundary and missing recovery capabilities

The active application stores all profiles, assignments, notes, exams, schedules, settings, and Sanctuary progress in one origin-local localStorage key (`src/store/storageKeys.ts:1`, `src/App.tsx:145`). Fishing/interaction statistics use additional per-profile localStorage keys (`src/game/systems/FishingSystem.ts:337`, `src/game/systems/KonoInteractionSystem.ts:401`). Profile filtering is organizational separation on one device, not authentication or independent user authorization.

Source inspection found no active user-data import/export/backup feature, server-side user-data persistence, login, cloud sync, cross-device recovery, or database. The only source `fetch` is weather (`src/game/weather/liveWeather.ts:93`). This is consistent with a personal local planner; it is insufficient for a hosted multi-user service or claims that data survives clearing browser data/changing devices/origins. Before real users depend on it, provide a validated versioned export/import round trip (including per-profile side stores where promised), documented local storage boundaries, and recoverable backups.

`Gentle reminders` at `src/App.tsx:329` is currently a saved checkbox/copy only; the setting is never consumed and there is no notification scheduler. If reminders are a release claim, implement and test them or correct the UI.
